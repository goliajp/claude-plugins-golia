# Appendix: where the gates came from

The protocol was run for several hundred rounds on one project — a compiler, with a remote runner for its heavy checks — before it was generalised. The numbers and incidents below are that project's; they explain the shape of each gate and are not defaults for anyone else ([adoption.md §4](adoption.md#4-calibrate)).

## A Calibration history

**The first gate turned into a quota.** The first version had one effective gate, a commit floor of 5. Measured over its last 60 rounds: commits per round min 5, p10 5, p50 6, p90 8, max 9 — nothing below the floor, nothing far above it. The left edge of the distribution was glued to the threshold: the gate had become the target. The redesign gave each gate a different question (floor, edges, content, wording, allocation) so that no two gates could be satisfied by the same move.

**Why the floor went to 12.** Every round pays a fixed cost that does not scale with commits: the close checks (about 18 min of machine time in that project), writing the handoff, rebuilding context on the far side. At the measured p50 (6 commits / 125 min) the machine floor alone was 14.7% of a round. Solving wall(N) = 18.4 + N × 17.8 from the same p50: N = 12 gives 232 min (7.9%), N = 20 gives 374 min (4.9%). Doubling to 12 took most of the recoverable overhead; 20 would have pushed the wall past the observed p90 (221 min) into a region no round had been measured in — and drift in exactly that region is why rounds exist. 12 was the far edge of the evidence, not a conservative choice.

**Why the floor grew a second measure.** The first eight rounds under N = 12 produced 13, 13, 14, 13, 13, 13, 14, 13 commits — eight of eight glued to the new threshold. Output per round had genuinely risen (median lines per round +48%), but the median commit had shrunk from 127 to 94 lines (−26%): a commit count is dilutable by construction. `closed:` entries are not, or far less so — each has to name a sha from this round and say what it closed in a sentence that survives being read. TRIG-1 kept the commit floor as the backstop and added a closed count of 3 as the real floor.

**Why the wall gate has both edges and is the only exit.** With a 12-commit floor, a round that spends five hours on one hard problem may never reach 12 and never close. The operator's manual trigger is not a path the model may take, so the exit had to be mechanical: past the wall cap the commit floor is waived. The same number doubles as "this round is long enough that drift now outweighs amortisation". The 30-minute floor catches the opposite failure — twelve trivial commits inside half an hour.

**What the thresholds actually caught.** Over the 127 rounds after the redesign: TRIG-1 bit on 3 rounds, all three released by the wall cap; 37 rounds (29%) reached the cap, 34 of which had ≥ 12 commits anyway; nobody fell below the 30-minute floor; the handoff was stale on 2. The correlation between wall and commits was 0.17: wall variance was mostly not work. The explanation found later was the idle gap between the trigger and the next session's first message — median 22 min, mean 101 min, about 37% of the wall in a 39-round sample. That is why the kernel now records `activeWallSec` separately from the trigger-to-trigger wall, and why a cap copied across projects, or across modes of the same project, measures something different.

**Why the axis gate is a review, not a forced switch.** A whole month of rounds served one axis; a second axis had received nothing for a month and a third had never started, and none of the five gates had asked which axis a round belonged to. Forcing a switch would have overridden the operator's plan; TRIG-5 instead removes the silence: every K rounds on the same axis, the handoff has to say where the other axes stand and carry the current reading. "Not run this round" is true and says nothing — the axis reading requirement exists because that sentence was written every round for a month while the axis in question had stood still within ±3% for fifty days.

**Why three gates read the repository instead of the handoff.** The first five gates read only what the handoff *said*. Three failures were therefore invisible to all of them: a check not run; a check run on the previous HEAD; last round's number carried into this round's handoff. The incident log had that class at least five times, including a sweep that stayed dark for five rounds while six pass regressions piled up, and a close that computed its deltas against the runner's stale baseline and produced a plausible, well-formed, completely false diff that took a round of A/B to disprove. TRIG-6 (stamps carry the sha they measured), TRIG-7 (the sweep line is re-derived and compared) and TRIG-8 (a `gate.end` event is the only evidence a gate ran) each close one of those holes. Stamps catch accidental failures that look exactly like success; a hand-written false stamp is a different offence and is not what they are for.

**The measuring instruments were broken too.** Two fields of the row had been dead for 900 rounds without anyone noticing: `commitsInSession` was a hard-coded `null` (the gate computed the number every call and threw it away), and the conformance probe read a file layout two profile generations old and returned empty every time. Both failures looked identical to "no data this round". The lesson became a rule: an instrument needs a cross-check that fails differently, and a gate without a self-test is a gate whose decay nobody sees.

## B Incidents and anti-patterns

- **Rotation as procrastination.** The original red handoff that the wording gate was written for: a trigger section that named no axis, no closed item and no gate reading, and argued for closing with "the remaining chunk is substantial work, a fresh session is more stable, the subagent prep is complete". Four gates failed it. The blacklist's kernel entries are the language-neutral residue of that incident; a project adds its own phrasings.
- **The manager that did substrate work.** A manager session, finding the executor unavailable, committed to the main tree itself "to save the handover cost". Nothing in the record said who had committed. `FOREIGN-COMMIT` (watchdog exit 14) and `managerCommits` in every row exist so that this is visible the moment it happens; the role rule says the only response to an unavailable executor is a new executor.
- **The watchdog that was reaped.** The reaper, walking the session's process tree at a close, killed the manager's own watchdog (it carried the same shell marker as any Bash-tool child) and the manager lost its wake-up. The reaper now keeps any shell whose subtree runs the kernel's `watchdog.sh`.
- **The watchdog that was reaped again.** The exception matched `<kernel directory name>/watchdog.sh`; a trial `trigger.sh self` run from a test subagent, using a copy of the kernel installed under a different directory name, walked up to the shared session process and ended fifteen shells — the manager's watchdog (run from the older install), the executor's pre-flight and its remote jobs. The exception now matches any `/watchdog.sh`, the reaper skips entirely while `manager.active` exists (a managed session's process is shared by design), and the documentation says where a trial round may run.
- **The wait nobody answered.** A worker's completion notice is delivered to the session that spawned the worker; the executor waiting on it stayed asleep until the manager forwarded the notice by hand, twice. The SubagentStop hook now records `agent.end` mechanically and the watchdog's WAKE reads it; and a `remote.end` followed by silence is a WAKE on its own, without an `executor.waiting` ever being written.
- **The resume that answered the wrong wait.** After a quota reset the manager had already continued the executor, but the watchdog kept reporting `QUOTA` because the manager's `SendMessage` left no event. `manager.resume` is now the event that answers QUOTA and WAKE.
- **The fill before the stamp.** A verdict was filled 51 seconds before a check re-stamped at HEAD; §3 said "not at HEAD" and judged it ok. "Not at HEAD" is now at least amber, and the order "stamp, then fill" is written into the close.
- **Two names for one report.** Executor reports were filed under the id the trigger had just opened on some rounds and under the round's own id on others. `report_save.sh` takes the closed round's id and refuses to overwrite.
- **A gate claimed, never recorded.** Gates were run by hand-written remote invocations for two rounds; no `gate.end` existed, and the verdict's "gate fails mid-round: none" was true on zero events. `adapter_run.sh` now refuses a success claim without its events, and a substrate range with no `gate.end` is red.
- **The side session that wrote to the live log.** A read-only analysis run against a live project appended a `close.plan` event to its real `events.jsonl`. Any kernel command run against a project from outside its rounds sets `ROTATION_EVENTS_LOG` to a throwaway copy first.

Anti-patterns the role rules name: a manager that outputs more than one line after a rotation; skipping the trigger; a model running `trigger.sh manual`; editing the handoff's wording to pass a gate; naming another round's sha on `closed:`; splitting commits to reach the floor; asking the operator for an override when a TRIG fails (the answer is to keep working).

## C Retired routes

Not in the plugin; listed so that nobody rebuilds them without reading why they went.

- **The marker file and the terminal watcher.** The Stop hook once wrote a marker file after INV-1..5 passed; a file-system watcher, installed as a LaunchAgent, sent `/clear` and a resume command to the terminal pane, waited for idle, and appended the inbox. It drove the model's terminal from outside, which coupled the kernel to one multiplexer and one machine, and it was never installed on the machine that ran the rounds. The intent file remains the Stop hook's sentinel; the handover is gated by the kernel and started by the manager.
- **Reaper by shell identity alone.** An earlier reaper identified child shells by a pattern that matched nothing on the then-current platform and reported `CLEAN` on every run — a dead probe whose output looked like a clean result. The current one walks the process tree and is tested for the one exception it must keep.
- **Thresholds from the environment.** The gates once read their thresholds from environment variables with built-in defaults; an executor could pass itself by setting one in the same shell, leaving no trace. The conf-only rule, the cleared environment and the `confSha256` in every row replaced it.
- **A per-project message table in the kernel.** The verdict's strings were once literal in the kernel, in one language. They are keyed now; a project overrides them through `ROTATION_MESSAGES`.
